# Combat Quality Rubric

**Module:** combat · **Version:** 1.0 · **Date:** 2026-06-22

**Back-test:** mean 0.00 / great 0.50 / gap 0.50 (thin great-hint; see report). **Re-validated** against a faithful top exemplar: mean 0.00 / great 0.97 / gap 0.97 → PASS. **Above-generic survival:** 29/29 (100%, strict unanimous-keep judge).

> Produced by `train-category` (research → strict above-generic judge → assemble → bias check → discrimination back-test → self-optimize → completeness critic). Text/design-claim-level grading; live capture/structure grading is the plugin loop (use_rubric + evaluate).

## Baseline

### marker-driven-event-timing

All combat gameplay events (hitbox activation, cancel windows, recovery start, VFX/SFX/hitstop triggers) are driven off named animation event markers via AnimationTrack:GetMarkerReachedSignal — NOT off wait()/task.delay timers or track.Length math. A non-programmer can move the impact frame in the editor and the gameplay re-syncs with zero code change.

- **Why above generic:** Surface check would be 'damage fires at the right time.' The systems-depth check is the DECOUPLING mechanism: hardcoded delays (wait(0.3)) drift with frame rate, AdjustSpeed, and replacement animations, visibly disconnecting hit from swing. Verifying markers (not timers) tests whether timing is structurally bound to the visual, which is the spine that lets every other feedback channel fire on one synchronized frame. The first play of an animation also reports Length 0, silently breaking length-based gating — markers sidestep this entirely.
- **Pass:** Attack timing (hitbox, cancel window, recovery, FX) is gated by named animation markers consumed via GetMarkerReachedSignal; a grep finds no wait()/task.delay/track.Length math driving the attack logic; moving the marker in the editor re-syncs gameplay with no code change.
- **Partial:** Markers are used for SOME events (e.g. hitbox) but other timing-critical events (cancel window or FX) still rely on wait()/task.delay or track.Length math; or markers exist but a length-based gate remains that breaks on first play (Length==0).
- **Fail:** Attack events are gated by wait()/task.delay/task.wait(track.Length...) timers rather than animation markers, so timing drifts with frame rate/AdjustSpeed and the hit decouples from the swing.
- **Evidence required:** Scripts use GetMarkerReachedSignal('HitFrame'/'CancelOpen'/'RecoveryStart') with named markers placed in the animation editor timeline; grep shows NO wait()/task.delay/task.wait(track.Length...) gating attack logic. Markers optionally carry a Parameter string.
- **Concrete fix:** Replace task.wait(0.3) damage delays with track:GetMarkerReachedSignal('HitFrame'):Connect(...) and place a 'HitFrame' marker at the contact keyframe in the editor.

### swept-active-frame-hitbox-no-touched

Hit detection is committed to an ACTIVE-FRAME model, not a swing-wide or .Touched model. The discriminating commitment, stated at the description level, is that the damage volume is LIVE ONLY during a narrow contact window inside the swing (gated by the same active-frame timing that drives FX) and DEAD during windup and recovery — NOT a volume that is 'active for the whole swing' and NOT BasePart.Touched. Above that floor, depth is shown by: a SWEPT spatial query that samples the weapon path between the previous and current frame (raycast/shapecast along the blade, or GetPartsInPart/GetPartBoundsInBox with OverlapParams) so fast swings cannot tunnel past thin targets, plus a per-swing already-hit set keyed by humanoid so each target takes exactly one hit per swing. A build whose hitbox is whole-swing-wide, instantaneous, or .Touched-based FAILS even if it deals damage; merely narrowing the window without swept sampling or dedup is PARTIAL.

- **Why above generic:** The mean artifact explicitly states the hitbox is 'active for the whole swing (no marker-synced active frames)' — a windup-and-recovery-wide volume — while the great artifact explicitly claims 'active frames driving hitboxes'. The original criterion's PASS evidence (swept query type, OverlapParams, hitList guard) is invisible in prose, so BOTH collapsed to fail and the criterion gave zero separation. Re-anchoring the discriminating axis on the active-frame-window COMMITMENT (which the great prose affirms and the mean prose explicitly rejects) lets the great artifact clear FAIL while the mean cannot, and preserves swept-sampling + dedup as the higher PASS bar so the ceiling stays at true systems depth rather than 'damage happens'.
- **Pass:** The hitbox is committed to a narrow active-contact window (live only during the strike, dead during windup/recovery), uses a swept spatial query sampling the weapon path between last and current frame positions (no .Touched), and has a per-swing humanoid-keyed hit-set so each target takes exactly one hit per swing.
- **Partial:** The description commits to active-frame windowing (not whole-swing, not .Touched) but is missing swept-path sampling (fast swings can tunnel) or the per-swing dedup set (one swing can multi-hit a rig).
- **Fail:** The hitbox is whole-swing-wide / instantaneous / windup-and-recovery-active, or uses BasePart.Touched, or has no contact-window commitment at all — damage is dealt but the active-frame model is absent.
- **Evidence required:** Description commits the hitbox to a narrow active-contact window (live only during the strike, dead in windup/recovery), NOT whole-swing and NOT .Touched. For full marks: swept-path sampling between last/current positions (raycast/shapecast/GetPartsInPart/GetPartBoundsInBox) defeating tunneling, plus a per-swing humanoid-keyed hit-set guaranteeing one hit per target per swing.
- **Concrete fix:** State that the damage volume activates only on the contact window (not the whole swing), sample the swept weapon path between frames with GetPartBoundsInBox/shapecast rather than .Touched, and add a per-swing hitList[humanoid] dedup so each target is hit once.

### layered-impact-sound-on-contact

Impact audio is layered and role-aware (whoosh on the swing, distinct thud/crunch/clang on connect, recognizable consistent parry/block cue) and the CONNECT sound fires on the contact-frame marker — not on swing start. Consistent interactions produce consistent, recognizable sounds.

- **Why above generic:** Surface check is 'there is a hit sound.' The depth check is WHEN it fires and whether it is layered: a connect sound played at swing-start (or a single undifferentiated clip) is the fastest tell of a generic system. Syncing the connect layer to the same contact marker as the hitbox, and keeping interaction sounds consistent so players learn them, is what makes hits read as decisive rather than mushy.
- **Pass:** Audio is layered (distinct swing-whoosh and connect-thud assets, plus a dedicated consistent parry/block cue) and the connect sound fires from the HitFrame contact marker, not at swing-start; consistent interactions produce consistent recognizable sounds.
- **Partial:** Distinct hit and swing sounds exist but the connect sound fires at swing-start rather than the contact marker; or sounds are layered but there is no dedicated/consistent parry-block cue.
- **Fail:** A single undifferentiated hit clip plays (no whoosh/connect separation) or the hit sound fires on swing-start instead of contact, so hits read as mushy and generic.
- **Evidence required:** Separate swing-whoosh and connect-thud assets; connect sound triggered from the HitFrame marker (same frame as hitbox), not at Activated/swing-start; a dedicated consistent parry/block sound exists; transient sounds parented to victim HRP with capped RollOffDistance.
- **Concrete fix:** Move the connect SoundService:PlayLocalSound/sound:Play call out of the swing-start handler into the HitFrame marker callback, and add a separate whoosh on the swing track.

### animation-priority-layering-coexist

Attacks, hit-reactions, dodges, and locomotion run as concurrently-blended tracks at deliberately-assigned AnimationPriority (e.g. attack Action4, victim hit-react Action3 so it does NOT cancel the attacker's swing, dodge Action2, locomotion Movement), relying on per-joint override + weight-normalized blending — NOT one full-body animation playing at a time.

- **Why above generic:** Surface check is 'animations play.' The depth check is COEXISTENCE: a generic build plays one full-body clip at a time, so attacking freezes movement and getting hit cancels your own swing. Correct priority layering is the prerequisite that makes attacker-keeps-swinging while victim-independently-flinches possible without manual blend code — it underpins both the hit-react and the attack-over-locomotion killer systems.
- **Pass:** AnimationPriority is explicitly assigned per clip (e.g. attack Action4, hit-react Action3, dodge Action2, locomotion Movement) so tracks coexist and blend; verified that a victim flinch does not cancel the attacker's active swing and attacking does not freeze movement.
- **Partial:** Priorities are set on some clips but left default on others, so partial conflicts remain (e.g. hit-react and attack share a priority and one cancels the other), or coexistence is not verified.
- **Fail:** Animations play one full-body clip at a time at default priority, so attacking freezes movement and getting hit cancels the attacker's own swing.
- **Evidence required:** AnimationPriority set explicitly per clip (Action4/Action3/Action2/Movement) rather than default; hit-react authored at Action3 so it doesn't override the attacker; verification that a victim flinch does not interrupt the attacker's active swing.
- **Concrete fix:** Set the hit-react track's Priority to Enum.AnimationPriority.Action3 and the attack to Action4 in the animation editor so the flinch layers without canceling.

### complete-combat-clip-set

The build OWNS a combat STANCE STATE MACHINE, not a flat list of attack clips. The discriminating, prose-readable commitment is an explicit non-combat<->combat state that the build ENTERS/EXITS on a signal (weapon draw / target acquired / first input) — holding a dedicated combat idle as the base armed state instead of leaving the stock idle — and a controller that DRIVES the combo/cancel/react vocabulary through this state (combos advance by index inside an authored window; cancel/active-frame timing is consumed by the controller, not guessed from clip length). A description that is 'a single canned attack' with 'no combo or cancel windows' and no armed stance FAILS. A description that asserts combos/cancels and a combat stance but does not commit to a controller that enters/exits combat on a signal and gates the windows is PARTIAL. An enumerated clip manifest (combat idle + transitions + index-named combo + launch/knockback react) and per-clip priorities/markers are credited toward PASS but never clear it alone — the discriminating commitment is the OWNED stance state machine that governs entry/exit and the windows, not the presence of clips.

- **Why above generic:** The mean artifact is 'a single canned attack' with 'no combo or cancel windows' — stateless, leaving the stock idle. The great artifact claims 'cancelable combo strings' but names no combat idle, no enter/exit signal, no controller. The original PASS gate (full clip manifest + state machine + GetMarkerReachedSignal consumption) is all structural, so the great artifact's real combo commitment landed in the same fail bucket as the mean's single canned clip. The rewrite keeps the load-bearing stance-state-machine as the PASS gate but introduces a PARTIAL rung for 'asserts combos/cancel-windows/armed stance without owning the controller', which the great prose reaches and the mean prose (single clip, no cancel windows) cannot — restoring separation while still reserving PASS for the genuinely systemic build.
- **Pass:** A controller OWNS an explicit non-combat<->combat state machine: enters/exits combat on a signal, holds a dedicated combat idle as base armed state, drives blended idle<->combat transitions, and consumes per-clip markers to gate combo/cancel windows where the chain advances by index — the clip vocabulary is wired into controller-governed states.
- **Partial:** The build commits to a combat stance plus cancelable/buffered combo strings with cancel windows (more than a single clip), but does not own the controller-level stance state — no signal-driven enter/exit, leaves the stock idle, or does not consume markers to gate the windows.
- **Fail:** A single canned attack with no combo or cancel windows and no armed combat stance (stock idle retained) — a stateless clip, even if multiple clips merely exist in a folder.
- **Evidence required:** For PARTIAL: the description commits to a combat stance plus cancelable/buffered combo strings (windows that exist, not a one-shot clip). For PASS additionally: a controller that owns an explicit non-combat<->combat state, enters/exits it on a signal, holds a combat idle as base armed state, drives blended idle<->combat transitions, and consumes per-clip markers (GetMarkerReachedSignal) to gate the combo/cancel windows; supporting clip manifest (combat idle, transitions, index-named combo, launch/knockback react).
- **Concrete fix:** Commit to an armed combat idle entered on weapon-draw/first-input, a controller that holds it as the base state and exits to non-combat on a signal, and combo/cancel windows the controller opens off per-clip markers — rather than a single canned swing with no cancel windows and the stock idle.

## Good (above the mean)

### anticipation-load-and-impact-hitstop

Every attack is built on a DELIBERATE timing-asymmetry skeleton AND a confirmed hit triggers a strength-scaled HIT-STOP. The discriminating, prose-readable commitment has two halves the mean explicitly rejects: (1) a held/loaded wind-up that accelerates from near-still into a single readable contact pose with peak velocity BEFORE the endpoint (not uniform interpolation), and (2) on contact, a hit-pause that briefly freezes/slows ONLY the attacker and victim animations while camera/particles/world keep moving, with pause length scaled by attack strength (light=short, heavy=longer). A description with 'no weighted wind-up, no hit-stop or freeze on contact' FAILS. A description that names weighted anticipation/follow-through AND hit-stop on impact clears FAIL (PARTIAL). PASS additionally requires the depth specifics: held/duplicate anticipation+contact keyframes, AdjustSpeed~0 scoped to attacker+victim only for a weight-scaled frame count, and broadcast so all clients freeze in sync.

- **Why above generic:** The mean artifact explicitly states 'no weighted wind-up, no hit-stop or freeze on contact'. The great artifact explicitly states 'weighted anticipation and follow-through with hit-stop/freeze-frames on impact'. This is the cleanest mean-vs-great split in the set, yet the original criterion's PASS list demanded keyframe-duplication, AdjustSpeed scoping, weight-scaling, and client-sync — none visible in prose — so the great artifact only reached PARTIAL and would have reached FAIL if the grader were strict. The rewrite makes the anticipation+hitstop COMMITMENT (which the great names and the mean negates) the explicit FAIL/PARTIAL boundary, guaranteeing separation, and keeps the structural detail as the PARTIAL→PASS ceiling.
- **Pass:** Attacks use the anticipation->contact->follow-through->recovery skeleton with held wind-up and held contact keyframes and peak velocity before the endpoint, AND a confirmed hit applies a strength-scaled hitstop to attacker+victim tracks only (AdjustSpeed~0 for a weight-scaled 1-4 frames) while camera/particles/world keep moving, broadcast so clients sync.
- **Partial:** The description commits to weighted/held anticipation with follow-through AND a hit-stop on contact, but lacks the depth specifics — hitstop is fixed-duration (not strength-scaled), freezes the world too, isn't client-synced, or the held-keyframe asymmetry is asserted without the contact-pose hold.
- **Fail:** No weighted/held wind-up and no hit-pause on contact (uniform interpolation, no freeze) — the attack reads as tapping with no readable contact frame.
- **Evidence required:** For PARTIAL: description commits to BOTH weighted/held anticipation with follow-through AND a hit-stop/freeze on contact. For PASS additionally: held or duplicated anticipation and contact keyframes, peak velocity before the endpoint, AdjustSpeed~0 applied ONLY to attacker+victim tracks for a strength-scaled frame count while camera/world continue, broadcast so clients freeze in sync.
- **Concrete fix:** Commit to a held wind-up that accelerates into a held contact pose, and on a confirmed hit AdjustSpeed~0 on attacker+victim tracks for a weight-scaled frame count (camera/world keep moving), broadcast via FireAllClients so all clients freeze together.

### weight-cues-body-drive-drag-followthrough

Strikes are committed to WHOLE-BODY weight transfer, not arm-only motion. The discriminating, prose-readable commitment is that the strike is described as DRIVEN BY THE BODY — torso/hip leading with the weapon arm dragging behind (overlap/drag), the body over-rotating slightly past the arm then re-centering, the weapon LINGERING past center in follow-through before a smooth (not brusque) recovery, with feet planted as a stable base (not gliding) — versus a swing where 'only the arm moves' and the pose snaps back. A description of a single canned click-swing with no weight cues FAILS. A description that commits to weighted, body-driven motion with anticipation and follow-through clears FAIL (PARTIAL). PASS requires the named mechanics: weapon arm keyed behind the torso (drag), a controlled non-sagging arc with over-rotation, a follow-through pose ~30-60deg past center, and hand-keyed planted feet (no auto-IK slide).

- **Why above generic:** The mean artifact is 'a single canned click-swing' with 'no weighted wind-up' — the canonical arm-only weightless look. The great artifact claims 'weighted anticipation and follow-through'. The original criterion demanded torso-lead/arm-drag/arc-over-rotation/planted-feet evidence (pure animation-craft detail), so the great artifact's weighted-motion commitment scored fail alongside the mean. The rewrite makes the body-driven-weight COMMITMENT the FAIL/PARTIAL boundary (great affirms it, mean's single canned swing negates it) and reserves the five named principles for PASS, keeping the systems-craft ceiling.
- **Pass:** Strikes are whole-body driven: torso/hip lead with the weapon arm dragging behind, a controlled non-sagging arc with over-rotation-then-recenter, a follow-through ~30-60deg past center, and hand-keyed planted feet — the named weight principles are present.
- **Partial:** The description commits to weighted, body-driven motion with anticipation and follow-through (more than arm-only) but does not specify the mechanics — missing arm-drag offset, arc over-rotation, follow-through linger, or planted feet.
- **Fail:** A single canned/arm-only swing with no weight cues that snaps back to rest — only the arm moves, reading as a weightless workout routine.
- **Evidence required:** For PARTIAL: description commits to weighted, body-driven strikes with anticipation and follow-through (not arm-only). For PASS additionally: weapon arm keyed a few frames behind torso rotation (drag/overlap), a clean non-sagging arc with over-rotation past the arm then re-center, a follow-through pose ~30-60deg past center before recovery, and hand-keyed planted feet (no auto-IK glide).
- **Concrete fix:** Describe the strike as torso/hip-led with the arm dragging behind, an arc that over-rotates then re-centers, a follow-through linger past center, and planted (hand-keyed) feet — instead of a single arm-only canned swing that snaps back.

### per-weapon-easing-and-pacing

Attack pacing is committed to being SHAPED, not a single fixed swing reused everywhere. The discriminating, prose-readable commitment has two parts the mean explicitly rejects: (1) the swing's timing is deliberately eased/contrasted across phases (a loaded accelerate-in, a crisp contact, an eased-out recovery) rather than one uniform/default speed, AND (2) swing speed reads from WEAPON MASS — heavier weapons are described as swinging materially slower/longer than lighter ones, not one swing duration for all. A description of 'one fixed' canned swing with uniform pacing across weapons FAILS. A description that commits to mass-/force-aware pacing where heavier weapons swing slower AND to phase-contrasted timing clears FAIL. PASS requires both verifiable: per-phase easing differentiation (windup ease-in, near-linear contact, ease-out recovery — not one uniform curve) AND a per-weapon frame budget (e.g. greatsword ~2x dagger).

- **Why above generic:** The mean artifact is 'one fixed' canned swing — the criterion's own named fail case ('one canned swing with uniform/default keyframe spacing FAILS'). The great artifact mentions 'force-aware' reactions but the original criterion required keyframe Style/Direction-per-phase and per-weapon frame counts, neither in prose, so it scored fail. Critically the original gives NO partial credit for the mass-aware-pacing commitment. The rewrite makes 'pacing reads from weapon mass + phase-contrast' the FAIL/PARTIAL boundary; the mean's explicit 'one fixed swing' negates it and a great artifact that commits to weapon-mass-scaled, eased pacing clears it, restoring separation.
- **Pass:** BOTH hold: per-phase easing is differentiated and verifiable (windup ease-in, near-linear contact, eased-out recovery — not one uniform curve) AND a per-weapon-weight frame budget makes heavier weapons span materially more frames than lighter, so swing speed reads from mass.
- **Partial:** The description commits to deliberately shaped/eased pacing AND to mass-scaled swing speed (heavier=slower) but without the specifics — easing not differentiated per phase, or weapon scaling asserted without distinct frame budgets.
- **Fail:** One fixed canned swing with uniform/default pacing reused across weapons (no mass scaling, no phase contrast) — the named fail case.
- **Evidence required:** For PARTIAL: description commits to deliberately shaped/eased pacing AND to swing speed scaling with weapon mass (heavier=slower/longer, not one fixed duration). For PASS additionally: per-phase easing differentiation verifiable (windup ease-in/Cubic-Sine, near-linear contact, eased-out recovery — not one uniform Style/Direction) AND a per-weapon-weight frame budget (heavier weapons span materially more frames, e.g. greatsword ~12-24f vs dagger ~6-12f).
- **Concrete fix:** Commit to easing the windup in, keeping contact near-linear, easing recovery out, AND give heavier weapons a longer frame budget than lighter ones (e.g. greatsword ~2x the dagger's span) instead of reusing one fixed swing for all weapons.

### directional-additive-hit-reaction

On hit the victim plays a directional flinch chosen by incoming hit vector (front/side/back variants) that snaps the silhouette AWAY from the attack, layered ADDITIVELY/at Action3 over the victim's current state (so it reads even while the victim is moving or attacking and does NOT cancel the attacker), as a brief (~0.3-0.5s) interruptible reaction distinct from ragdoll — paired with a small position delta via root motion or impulse.

- **Why above generic:** This is the 'directional-hit-reactions-and-knockback' killer system (reaction half). Surface check is 'something plays when hit.' The depth check is DIRECTIONALITY + ADDITIVE LAYERING: in generic systems the victim just loses HP and keeps their idle/run, so hits read as ignored. A flinch that snaps in the hit direction proves the hit connected AND from where (Newton's-third-law read); doing it additively at Action3 keeps it from looking robotic and from canceling the attacker's swing — directly depending on the priority-layering baseline.
- **Pass:** On hit the victim plays a directional flinch selected from front/side/back clips by the incoming hit vector, snapping the silhouette away from the attack, layered additively/at Action3 over the current state (brief ~0.3-0.5s, interruptible, does NOT cancel the attacker) with a small accompanying position delta.
- **Partial:** A flinch plays on hit but is non-directional (single clip regardless of hit angle), OR is directional but plays at a priority that cancels the attacker's swing or replaces the victim's locomotion rather than layering additively.
- **Fail:** The victim just loses HP and keeps its idle/run with no reactive flinch, so hits read as ignored.
- **Evidence required:** Hit-react selected from front/side/back clips by computing the hit direction relative to victim facing; played at Action3 (additive/overlay), brief and interruptible; verified not to cancel the attacker's track; small root/impulse position delta accompanies it.
- **Concrete fix:** Compute dir = victimHRP.CFrame:VectorToObjectSpace(attackerHRP.Position - victimHRP.Position) and pick FlinchFront/Left/Right/Back accordingly, playing it at Action3 priority.

### hitstun-and-walkspeed-commitment

A confirmed hit is committed to imposing real COMMITMENT/CONSEQUENCE on the exchange, not just a cosmetic flinch the victim can mash through. The discriminating, prose-readable commitment is that on-hit consequence is described as REACTIVE AND FORCE-COUPLED across BOTH parties: the victim is force-reacted/displaced (force-aware reaction AND knockback that moves them, breaking their current action's continuity) so the exchange reads as give-and-take rather than two players trading idle/run frames. A description whose ONLY on-hit consequence is 'one fixed flinch reaction' with no force coupling and no displacement (victim keeps full agency) FAILS. A description that commits to direction-/force-aware reactions PLUS knockback that displaces the victim on hit (coupling the reaction to a real position consequence) clears FAIL. PASS requires the true hit-stun STATE: a server-authoritative stun attribute/flag with timed cleanup that GATES the victim's own attack AND block for a defined window, plus attacker WalkSpeed self-root during the swing; a client BoolValue or a displacement-only consequence with no action-lockout is PARTIAL.

- **Why above generic:** Surface check is 'something happens on hit.' The systems-depth check is whether the hit imposes a STATE/POSITION consequence that constrains the victim, versus a cosmetic flinch the victim ignores. Anchoring FAIL/PARTIAL on force-coupled displacement (reaction tied to knockback) is recoverable from the great prose ('force-aware hit reactions AND knockback') and explicitly negated by the mean ('one fixed flinch'), while reserving server-authoritative action-lockout for PASS keeps the ceiling at true give-and-take combat rather than 'the victim gets pushed'.
- **Pass:** A confirmed hit sets a server-authoritative stun state (attribute/flag with timed/Debris cleanup) that gates the victim's OWN attack and block for a defined duration so they cannot mash through, plus attacker WalkSpeed self-root during the swing — the exchange has enforced commitment on both sides.
- **Partial:** On-hit consequence couples a direction-/force-aware reaction to knockback that displaces the victim (a real position consequence, not a free flinch), but the action-lockout is client-side/exploitable (BoolValue) or absent — the victim is displaced but not server-gated out of attacking/blocking.
- **Fail:** The only on-hit consequence is a cosmetic, displacement-free flinch (e.g. 'one fixed flinch regardless of direction') the victim can act through — no force coupling, no knockback, no action lockout.
- **Evidence required:** For PARTIAL: description couples the on-hit reaction to a real consequence — direction-/force-aware reaction PLUS knockback that displaces the victim, breaking their action continuity (not a cosmetic, displacement-free flinch). For PASS additionally: a server-authoritative stun attribute/flag with timed/Debris cleanup that gates the victim's OWN attack AND block for a defined window, plus attacker WalkSpeed reduced during the swing and restored on a recovery marker.
- **Concrete fix:** Couple the flinch to knockback that actually displaces the victim, then escalate to a server-authoritative Stunned attribute (timed clear) that gates the victim's attack and block handlers and reduce the attacker's WalkSpeed for the swing — rather than playing only a displacement-free cosmetic flinch the victim can mash through.

### marker-synced-impact-fx-stack

At the single contact-frame marker, a multi-channel impact stack fires together and client-side-immediately: a one-shot directional, camera-facing particle/debris/slash-decal burst at the exact contact point (emitters Enabled=false, cloned to victim HRP, :Emit(count) per child, Debris-cleaned), a SUBTLE strength-scaled directional camera shake/tilt with falloff (via a shake module, not constant max-intensity), restrained on-hit UI accents (brief tweened screen flash, target highlight/outline flash, reactive health bar), and a contact accent on the rig (1-2 frame limb tremor and/or squash-on-victim/stretch-on-attacker) — all scaled by attack power.

- **Why above generic:** This is the 'marker-synced-active-frames-and-impact-fx' killer system (the FX half). Surface check is 'there are particles/shake.' The depth check is SYNCHRONIZATION TO THE CONTACT MARKER + SCALING + RESTRAINT: default systems have no impact VFX (or a reused smoke puff), a dead-still camera, and only a ticking damage number. Firing all channels off the same HitFrame marker as the hitbox/hitstop, scaling each by power, running cosmetics client-side so the felt impact never waits on the server, and the one-shot Enabled=false :Emit idiom (vs a wrongly-streaming emitter) are the concrete tells. Critics explicitly warn constant max shake / heavy full-screen effects get 'nauseating very quick,' so the above-generic version is subtle and scaled, not just 'add screenshake.'
- **Pass:** A multi-channel impact stack (one-shot contact-point particle/decal burst via Enabled=false + :Emit, subtle strength-scaled camera shake with falloff, restrained UI accents, and a rig contact accent) all fires from the SAME HitFrame marker as the hitbox, scaled by attack weight, run client-side immediately (not gated on server round-trip), and Debris-cleaned.
- **Partial:** Some impact channels exist but are not all synced to the contact marker (e.g. fire on swing-start), are not weight-scaled, use constant max-intensity shake/streaming emitters instead of one-shot :Emit, or wait on a server round-trip.
- **Fail:** No impact VFX (or a reused smoke puff), a dead-still camera, and only a ticking damage number on hit.
- **Evidence required:** Particle burst, camera shake, screen flash/target highlight, and limb-tremor/squash all triggered from the SAME HitFrame marker as the hitbox; magnitudes parameterized by attack weight; emitters use Enabled=false + per-child :Emit(EmitCount attribute); camera shake uses a falloff module and stays subtle/toggleable; cosmetic channels run on the client immediately (FireAllClients), not gated on server round-trip; transients cleaned via Debris.
- **Concrete fix:** In the HitFrame marker handler, FireAllClients a single 'impact' event carrying weight, and have clients run shake(weight), emitBurst(contactCFrame, weight), flashTarget(victim), and a 2-frame limb AdjustSpeed tremor — all keyed to that one frame.

### connected-combo-chain-flowing-poses

The M1 combo reads as ONE continuous motion, not N separate clips played back-to-back: every clip's final pose is re-keyed to match the next clip's opening pose (no snap/teleport between hits), the attacks are genuinely distinct in silhouette and momentum (e.g. jab -> hook -> uppercut -> launcher) and ESCALATE into a finisher so the chain has a deliberate wind-up-to-payoff arc rather than a uniform repeated swing, and the chain advances/cancels off an animation MARKER (e.g. a 'CancelOpen'/'NextWindow' event keyed in the clip), NOT off clip Length minus a magic constant. The criterion is met only when the cancel window is marker-driven (so it survives the first-play Length==0 case and is authored per-clip rather than guessed) and the inter-clip transitions are visibly seamless on capture. Index/string-built clip lookup is an acceptable scalability implementation but is NOT itself evidence of above-generic quality — pose continuity, the escalation arc, and marker-gated cancels are.

- **Why above generic:** Surface check is 'clicking multiple times plays multiple animations.' The depth check is POSE CONTINUITY + VARIATION + ARC: a single repeated swing is the hallmark generic look; recovery that's too brusque looks unfinished while too-long recovery feels sluggish. End-pose-into-next-start-pose makes the whole combo read as one fluid sequence, varied attacks plus a distinct finisher give it a build-to-payoff arc, and index-named lookup is the scalable structure.
