# Locomotion Quality Rubric

**Module:** locomotion · **Version:** 1.1 · **Date:** 2026-06-20

**Back-test:** mean 0.00 / great 0.82 / gap 0.82 → PASS (3 optimization round(s)). **Above-generic survival:** 16/21 (76%, strict judge).

> Produced by `train-category` (research → strict above-generic judge → assemble → bias check → discrimination back-test → self-optimize → completeness critic). Text/structure-level grading; live capture grading is the loop session.

## Baseline

### loco-state-machine

Locomotion routing is governed by a velocity-classifying control layer the build OWNS, not the stock single-loop default. To pass, the build must commit at the architecture level to a routing layer that reads live planar velocity (and/or Humanoid MoveDirection/state) and selects/weights among MORE THAN ONE locomotion target from that signal — e.g. a blend tree keyed to planar velocity, or a custom Animate-override controller with per-state tables driven by velocity. The single discriminating commitment is: clip selection is a function of a live continuous movement signal, NOT a discrete WalkSpeed-keyed swap of one forward clip on the untouched stock Animate. A build that states locomotion is a single forward walk/run loop swapped by WalkSpeed on default Animate FAILS; a build that states a velocity-driven blend/controller owns selection PASSES (capture/dump strengthens but is not required at the design-claim stage — the architectural commitment is what is graded).

- **Why above generic:** The engine gives every game the stock Animate with one forward loop swapped by WalkSpeed for free — that is exactly the floor and exactly the mean. The above-generic move is owning a routing layer whose input is a live continuous velocity signal feeding multi-target selection; this is the seam every other locomotion system (blend, IK, aim) composes onto. Grading the architectural commitment (velocity-driven multi-target routing vs. WalkSpeed clip-swap) — rather than demanding a runtime dump a design-stage artifact cannot have — is what separates a real systems architecture from inheriting the default, while still beating what is free.
- **Pass:** The build commits to a routing layer it owns (custom controller or extended Animate override) that selects/weights >1 locomotion target as a function of live planar velocity / MoveDirection — e.g. a velocity-keyed blend tree; a dump or capture is credited but not required to pass at the design-claim stage.
- **Partial:** An owned routing layer is claimed but its input is a discrete threshold (e.g. WalkSpeed buckets) rather than a continuous live-velocity signal, OR it routes only a single state beyond idle.
- **Fail:** Stock Animate left untouched with the walk/run slots pointed at one forward clip swapped by WalkSpeed; no velocity-driven owned routing layer.
- **Evidence required:** A statement/dump/code showing an owned routing layer (custom controller or named Animate override) whose clip selection/weighting is a function of LIVE planar velocity or MoveDirection across more than one target (a velocity-keyed blend tree qualifies). A description that the stock Animate is untouched with one forward clip swapped by WalkSpeed does NOT satisfy this. A runtime capture is credited but not required at the design-claim stage.
- **Concrete fix:** Replace the WalkSpeed clip-swap with a routing layer you own — a velocity-keyed blend tree or a custom Animate-override controller — whose target selection is a continuous function of live planar velocity, and make it the documented hook point for blend/IK/aim.
- **Exemplar refs:** https://github.com/Roblox/creator-docs/blob/main/content/en-us/tutorials/use-case-tutorials/animation/play-character-animations.md, https://www.youtube.com/watch?v=sr34MYv35XU

### loco-living-idle

Idle is a first-class node in the locomotion control system, distinct from the movement loop. The discriminator is whether the build's architecture HAS a zero-velocity idle state at all: passing requires (1) idle present as its own node selected when planar speed is at/near zero (the v=0 endpoint of the blend space counts), AND (2) idle treated as the base layer that additive standing aim/lean ride on. A build that describes locomotion purely as a movement loop with NO idle node, or that bolts idle onto the stock single-forward-clip default with no v=0 state in an owned controller, FAILS. A build whose velocity-driven blend space includes idle@0 as its low end and composes the standing aim/lean over it PASSES at the architecture level; an authored breathing/weight-shift loop and a capture raise it toward exceptional but are not the pass gate (this is the baseline existence check, not the polish check).

- **Why above generic:** A clip-swap-by-WalkSpeed build has no authored v=0 node — idle is whatever the default leaves. The above-generic move is treating idle as the explicit low end of a velocity blend space that the additive standing layers compose onto. Grading the EXISTENCE of an owned idle@0 node (not demanding a breathing-loop capture a design-stage build cannot show) keeps this a real baseline discriminator: a velocity-blend architecture inherently has an idle@0 endpoint, a forward-loop-by-WalkSpeed build does not.
- **Pass:** Idle exists as an explicit zero-velocity node / blend-space low end in an owned controller AND is the base the additive standing aim/lean ride on; an authored living loop and capture are credited but not required to pass.
- **Partial:** An owned controller exists and reaches a near-zero state, but idle@0 is not called out as a distinct node OR it is not yet composed with the standing additive layers.
- **Fail:** Locomotion is movement-only with no idle node, or idle is a frozen/looped neutral default pose on the untouched stock Animate.
- **Evidence required:** A statement/dump showing idle as an explicit zero-velocity node (or the v=0 low end of the owned blend space) AND that the standing aim/lean additively layer over this idle base. Absence of any idle node, or reliance on the stock default neutral pose, fails. An authored breathing/weight-shift capture is credited toward higher tiers but is not required for the baseline pass.
- **Concrete fix:** Make idle the explicit v=0 node of your owned locomotion controller (the low end of the speed blend space), and ensure the additive aim/lean layers blend over this idle base while standing; then author a breathing + weight-shift loop to push beyond baseline.
- **Exemplar refs:** https://devforum.roblox.com/t/idle-animation-feedback/1325333, https://www.youtube.com/watch?v=6lGPvMLE8Oo

## Good (above the mean)

### loco-stride-locked-to-speed

Contact-phase foot skating is solved by the locomotion system, not left to a fixed-rate clip — either by coupling playback cadence to live velocity OR by a runtime contact-grounding pass that fixes the foot's WORLD position through the stance phase. The discriminator is whether the build commits to ANY runtime mechanism that keeps the planted foot from sliding relative to the ground: passing requires the build to state at least one of (1) AnimationTrack:AdjustSpeed (or equivalent per-frame cadence scaling) driven from the same live planar-velocity signal the locomotion uses (animSpeed approx speed/baseline), so cadence tracks translation; OR (2) a runtime foot-grounding/IK pass (IKControl Transform or Motor6D.Transform) that plants the stance foot to the WORLD on slopes and steps so it does not skate during contact. A build that swaps/scales one fixed-rate forward clip by WalkSpeed with neither cadence coupling nor a grounding pass — i.e. one whose own description is that feet skate on slopes — FAILS. A build that commits to either the velocity->cadence coupling OR a world-planting foot-IK pass PASSES; committing to both (cadence lock AND world-plant) is the strongest and pushes toward full marks.

- **Why above generic:** Generic packs play a fixed-rate clip whose feet slide whenever cadence or ground angle disagrees with translation — the mean, and exactly what the engine leaves you. The above-generic move is a runtime mechanism that ties the foot to the ground: either cadence coupled to the same live velocity the system already computes, or a world-planting IK pass that nails the stance foot through contact. Either is a runtime control-loop the MEAN's WalkSpeed clip-swap structurally cannot express, so crediting either (while still failing the self-described skating build) keeps this a genuine anti-skate discriminator.
- **Pass:** The build commits to at least one runtime anti-skate mechanism: AdjustSpeed-from-live-velocity cadence coupling, OR a world-planting foot-IK/grounding pass on slopes/steps; both together is strongest.
- **Partial:** An anti-skate intent is claimed but the mechanism is vague (e.g. 'feet match the ground somehow') with neither AdjustSpeed-from-velocity nor an IK/Transform world-plant named, OR grounding is flat-ground-only with no slope/step handling.
- **Fail:** Fixed-rate clip swapped/scaled by WalkSpeed with neither velocity->cadence coupling nor a world-planting grounding pass; the self-described 'feet skate on slopes' case.
- **Evidence required:** A statement/code showing EITHER (1) AdjustSpeed (or equivalent cadence rate) driven from live velocity/baseline, OR (2) a runtime foot-grounding pass (IKControl Transform / Motor6D.Transform) that plants the stance foot to the world on slopes/steps so it does not slide during contact. A fixed-rate clip swapped/scaled by WalkSpeed with neither mechanism — or an explicit 'feet skate on slopes' description — does NOT satisfy this.
- **Concrete fix:** Either drive AdjustSpeed(velocity/baseline) each frame from your live velocity signal so cadence tracks translation, OR add a runtime foot-IK grounding pass that fixes each stance foot to its world contact point on slopes and steps; commit to both to fully eliminate contact skate.
- **Exemplar refs:** https://devforum.roblox.com/t/how-to-make-animation-consistent-with-walkspeed/2713407, https://mocaponline.com/blogs/mocap-news/locomotion-animations-game-dev

### loco-directional-variant-set

Movement direction is decoupled from facing by a direction-axis blend driven by velocity projected into the rig's local frame — not one forward clip rotated onto all input. The discriminator is whether the architecture commits to a 2D direction axis fed by object-space velocity: passing requires the build to state (1) a direction blend that selects/weights among directional targets (forward/back + left/right strafe; diagonals ideal) and (2) selection driven by velocity projected into HumanoidRootPart object space (CFrame:VectorToObjectSpace) or dot/cross of velocity vs look/right, so the correct variant blends in for every direction with no moonwalk. A build stated as 'forward-only clips' with no strafe/directional set FAILS. A build that commits to a velocity-into-local-frame direction axis (e.g. a 2D blend keyed to planar velocity covering forward+strafe) PASSES at the architecture level; an enumerated per-speed-state clip inventory and a 4–8-direction capture strengthen it toward exceptional but the bare object-space direction-axis commitment clears the pass gate, whereas a 'directional blend' asserted with NO velocity-projection mechanism does not.

- **Why above generic:** Generic builds ship one forward clip and rotate the body — the moonwalk that defines mean locomotion, and exactly what the engine leaves you. The above-generic move is a direction axis fed by velocity projected into the rig's local frame so movement decouples from facing. Grading the object-space-velocity direction-axis commitment (not demanding a full enumerated inventory + capture a design-stage build lacks) keeps this an architecture discriminator a 2D-velocity blend satisfies and a forward-only clip-swap cannot.
- **Pass:** The build commits to a direction axis whose selection/weighting is driven by velocity projected into local frame (VectorToObjectSpace or dot/cross of velocity vs look/right) covering at least forward/back + strafe; an enumerated per-state inventory and a multi-direction capture are credited but not required to pass.
- **Partial:** A directional/strafe blend is claimed but the velocity-projection selection mechanism is not stated (just a 'forward+strafe' label), OR coverage is partial so some directions still moonwalk.
- **Fail:** Forward-only clips with no directional set; OR one forward clip rotated onto all movement; moonwalk on non-forward input.
- **Evidence required:** A statement/dump of a direction axis driven by object-space velocity projection (VectorToObjectSpace or dot/cross of velocity vs look/right) covering ≥ forward/back + strafe; OR a 4–8-direction capture with no moonwalk; OR an enumerated forward/back/left/right(/diagonal) per-state inventory tied to that selection. A 'forward+strafe' label with NO velocity-projection mechanism, or one forward clip rotated onto all directions, does not satisfy this.
- **Concrete fix:** Add a direction axis whose weights come from VectorToObjectSpace(velocity)/WalkSpeed (or dot/cross of velocity vs look/right), covering forward/back + left/right strafe (then diagonals), so movement direction decouples from facing with no moonwalk.
- **Exemplar refs:** https://devforum.roblox.com/t/default-r15-player-animations-now-include-strafing-and-backpedaling-beta/1999236, https://mocaponline.com/blogs/mocap-news/locomotion-animations-game-dev

### loco-per-part-easing

Limb motion is shaped per body-region rather than as one undifferentiated baked timeline, so the gait reads weighted instead of mechanical. Because per-clip tangent authoring is not capturable from a design-stage build, the discriminator is whether the build applies per-region differentiation to the clip at all — by EITHER (1) authored selective per-part interpolation (extremities/arms/head eased with end-of-swing ease-out, torso/legs near-linear so cadence never hitches, plus moving-holds so no joint freezes), OR (2) a runtime stack of region-targeted overlays that drive different body regions independently of the leg cycle (e.g. an additive upper-body aim/look-at layer for arms/head AND an accel/gait-phase torso-or-pelvis layer), so the upper body is differentiated from the legs at runtime rather than welded to one baked timeline. A build that plays raw library clips as-is with ONE baked interpolation and NO per-region differentiation (no authored per-part easing AND no region-targeted runtime overlays) FAILS. A build that commits to authored per-part easing OR to >=2 independent region-targeted runtime overlays over the clip PASSES; a per-joint tangent dump or slow-playback capture strengthens it toward full marks.

- **Why above generic:** Raw library clips (the mean) get one baked interpolation and move every region on the same undifferentiated timeline. The above-generic craft is region-specific shaping — either authored ease differences plus moving-holds, or a runtime stack that drives upper-body regions on separate layers from the legs. Crediting >=2 independent region-targeted runtime overlays (while refusing both raw-clips and a single-layer build) keeps this a real per-region discriminator a layered runtime architecture clears and a one-baked-clip build cannot.
- **Pass:** The build commits to authored differentiated per-part interpolation (eased extremities, near-linear legs/torso, moving-holds) OR to a runtime stack of >=2 region-targeted overlays driving distinct body regions independently of the leg cycle; a tangent dump/capture is credited but not required.
- **Partial:** Some per-region differentiation is implied but thin — only ONE runtime overlay over the clip (upper body not split from a second region), OR vague 'smoothed motion' with no extremity-vs-legs distinction and no moving-holds.
- **Fail:** Raw library clips played as-is with one baked curve and no per-region treatment — neither authored per-part easing nor any region-targeted runtime overlay.
- **Evidence required:** EITHER (1) a statement of authored selective per-part interpolation (eased arms/head vs near-linear legs/torso + moving-holds) on the clips; OR (2) a stated runtime stack of at least two region-targeted overlays driving different body regions independently of the leg cycle (e.g. additive upper-body aim/look-at for arms/head AND an accel/gait-phase torso/pelvis layer). Raw clips played as-is with one baked curve and a single (or zero) runtime layer do not satisfy this; a tangent dump / slow-playback capture is credited toward full marks but not required.
- **Concrete fix:** Either author your clips with eased arm/head curves (end-of-swing ease-out), near-linear leg/torso, and moving-hold keys; or layer at least two region-targeted runtime overlays over the library clips (an additive upper-body aim/look-at for arms/head plus an accel/gait-phase torso/pelvis layer) so the upper body is shaped independently of the legs.
- **Exemplar refs:** https://devforum.roblox.com/t/feedback-on-my-walk-animation/2781799, https://www.youtube.com/watch?v=TMeQQYcB2Cg

### loco-blend-tree-speed-and-direction

KILLER SYSTEM — BLEND TREE. Locomotion warps continuously by speed AND direction through a velocity-driven blend space, not hard clip swaps. The discriminator is whether the build COMMITS to both axes driven by live velocity: passing requires the build to state (1) a speed axis (idle@0 → walk → jog → run) that crossfades adjacent tiers rather than threshold-swapping, AND (2) a direction axis that weights directional targets by velocity projected into HumanoidRootPart object space (VectorToObjectSpace; X=strafe, Z=fwd/back) or dot/cross of MoveDirection vs look/right. A build of one forward loop swapped by WalkSpeed (no crossfade, no direction axis, no relative-direction computation) FAILS. A build that commits to a 2D blend keyed to planar velocity covering speed AND forward+strafe PASSES at the architecture level; the per-frame AdjustWeight/AdjustSpeed wiring, the Epsilon-weight clamp, and a pop-free acceleration+direction-sweep capture strengthen it toward full marks but the dual-axis velocity-driven blend commitment clears the pass gate. A single-axis-only blend (speed but no direction, or vice versa) earns partial.

- **Why above generic:** This is the headline killer system. The engine hard-swaps idle→walk→run on a speed threshold and has no notion of relative direction (moonwalk) — the floor. A velocity-driven 1D-speed + 2D-direction blend space with weight-blended same-priority tracks is the AAA locomotion blend tree adapted to Roblox. The object-space projection and dual-axis commitment are the concrete, gradable mechanisms; grading the architectural commitment (rather than demanding the AdjustWeight/Epsilon capture a design-stage build can't show) keeps the killer system discriminating: a 2D-velocity blend clears it, a WalkSpeed clip-swap cannot.
- **Pass:** The build commits to BOTH a velocity-driven speed axis (crossfading tiers) AND a direction axis weighted by object-space/dot-product velocity; the AdjustWeight/AdjustSpeed wiring, Epsilon clamp, and a pop-free capture are credited but not required to pass at the design-claim stage.
- **Partial:** Only one axis is committed (speed crossfade but direction hard-switches, or directional blend but speed tiers snap), OR both axes named but with no velocity-projection mechanism (a bare 'blend tree' label).
- **Fail:** One forward loop scaled/swapped by WalkSpeed; hard clip swaps at fixed thresholds; no relative-direction computation.
- **Evidence required:** A statement/dump showing BOTH axes driven by live velocity — a crossfading speed axis AND a direction axis weighted by VectorToObjectSpace/dot-product velocity. The per-frame AdjustWeight (Epsilon-clamped) + AdjustSpeed wiring and a pop-free acceleration+direction-sweep capture are credited toward full marks but are not required for the pass gate. A bare 'blend tree' label with no velocity-projection mechanism, or one forward loop by WalkSpeed, do not satisfy this.
- **Concrete fix:** Commit to a 1D speed blend (crossfade adjacent tiers by weight) AND a 2D direction blend (weight variants by VectorToObjectSpace(velocity)/WalkSpeed or dot/cross); then wire per-frame AdjustWeight (Epsilon-clamped, never exactly 0) + AdjustSpeed and verify a pop-free acceleration and direction sweep.
- **Exemplar refs:** https://mocaponline.com/blogs/mocap-news/locomotion-animations-game-dev, https://www.youtube.com/watch?v=aP_VzBxrPOA, https://devforum.roblox.com/t/8-way-directional-movement-system-for-r6-1-animation/2656069

### loco-foot-ik-terrain

KILLER SYSTEM — FOOT IK. Feet plant on the actual ground, slopes, and steps via runtime IK layered over the canned clip — no skating, no floating. The discriminator is whether the build commits to a runtime, world-influenced foot-grounding pass: passing requires the build to state foot planting via engine-native IKControl (Type Transform; EndEffector=foot, ChainRoot=upper-leg, Target=downward-raycast hit) OR Motor6D.Transform offsets, where the IK overlay corrects feet to the WORLD on top of the clip (the clip carries style). A build that states 'no foot IK / feet skate on slopes' FAILS — direct contradiction. A build that commits to runtime foot IK via IKControl/Motor6D that plants feet on slopes and steps PASSES at the architecture level; the surface-normal alignment, raycast-from-animated-hip, slope-angle reject (~45°), per-state Weight/SmoothTime modulation, and a slope+stairs capture push it toward full marks but the runtime-IK-grounding commitment clears the pass gate. A claim with the wrong/absent mechanism (e.g. just 'feet snap to ground' with no IK/Transform path) earns partial.

- **Why above generic:** Second killer system and the most-cited showcase realism technique. Baked clips float over slopes/stairs and skate on uneven ground; the engine ships no foot IK — that is the floor. World-influenced foot planting via IKControl/Motor6D.Transform layered over the clip is what separates animation that ignores the world from animation that responds to it. Grading the runtime-IK-grounding commitment (rather than demanding an instance dump + slope capture a design-stage build can't produce) keeps the killer system discriminating: a build that commits to foot IK clears it; one that states 'feet skate, no IK' cannot.
- **Pass:** The build commits to a runtime foot-grounding pass via IKControl (Transform) or Motor6D.Transform layered over the clip, planting feet on slopes/steps; surface-normal alignment, raycast-from-animated-hip, slope reject, per-state Weight/SmoothTime, and a capture are credited but not required to pass.
- **Partial:** Foot grounding is claimed but the mechanism is unstated or non-IK (e.g. 'feet snap down') OR it is flat-ground-only with no slope/step handling implied.
- **Fail:** No IK; feet float over slopes/steps and skate on uneven ground (the explicit 'no foot IK, feet skate' case).
- **Evidence required:** A statement/dump showing a runtime foot-grounding pass via IKControl (Type Transform, EndEffector/ChainRoot/Target) or Motor6D.Transform layered over the clip, planting feet on slopes/steps. The surface-normal alignment, raycast-from-hip + slope-reject + per-state Weight/SmoothTime logic, and a slope/stairs capture are credited toward full marks but not required for the pass gate. An explicit 'no foot IK / feet skate' description fails.
- **Concrete fix:** Add an IKControl per foot under the Animator (Transform, ChainRoot=upper leg, Target from a downward raycast off the animated hip), align the foot to the ray normal, reject surfaces past ~45°, and modulate Weight/SmoothTime by movement state; or apply equivalent Motor6D.Transform offsets as an additive layer over the clip.
- **Exemplar refs:** https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/IKControl.yaml, https://devforum.roblox.com/t/prototype-r15-animation-ikcontrol-footplant/2187090, https://devforum.roblox.com/t/free-r15-ikpf-system-inverse-kinematics-procedural-footplanting/706574

### loco-additive-lookat-aim

KILLER SYSTEM — ADDITIVE LOOK-AT / AIM. An additive look-at/aim layer rides ON TOP of running locomotion (head/torso/arms orient to a target) without stopping or replacing the gait. The discriminator is whether the build commits to a LAYERED upper-body aim that leaves the legs walking: passing requires the build to state an aim/look-at implemented as an additive layer — via an IKControl aim chain, an AnimationConstraint driving the aim joints, OR AnimationPriority layering (locomotion on Movement, aim on Action+ so only conflicting limbs are overridden) — explicitly NOT a track that stops/restarts the walk. A build that states 'no additive look-at' FAILS. A build that commits to an additive aim/look-at layer over locomotion PASSES at the architecture level; the track-priority dump (Movement vs Action+) or IKControl aim-chain config and a walk-while-tracking capture strengthen it toward full marks but the additive-layer commitment clears the pass gate. A build whose aim stops/replaces the whole-body gait earns partial.

- **Why above generic:** Third killer system. Generic code STOPS the walk track to play an action/aim then restarts it — jarring and bug-prone — because it ignores the priority ladder; that is the free behavior. Layering an additive aim/look-at over locomotion (IKControl aim chain, AnimationConstraint, or Core<Idle<Movement<Action priority) so only the upper body re-orients while the legs keep their gait is a top-studio touch absent from any canned cycle. Grading the additive-layer commitment (not demanding a priority dump + capture a design-stage build lacks) keeps the killer system discriminating: a build that commits to the additive aim clears it; one that says 'no additive look-at' cannot.
- **Pass:** The build commits to an additive aim/look-at layer (IKControl aim chain, AnimationConstraint, or Movement-under-Action priority layering) so the upper body orients while locomotion keeps running; a priority dump / aim-chain config and a walk-while-tracking capture are credited but not required to pass.
- **Partial:** An aim/look-at is claimed but it stops/restarts the walk track OR overrides the whole body instead of only the upper limbs.
- **Fail:** No look-at/aim layer (the explicit 'no additive look-at' case); or the gait is killed whenever the character looks/aims.
- **Evidence required:** A statement/dump showing an additive aim/look-at layer that leaves locomotion running — via an IKControl aim chain, an AnimationConstraint, or AnimationPriority layering (locomotion=Movement, aim=Action+). A track-priority dump or aim-chain config and a walk-while-tracking capture are credited toward full marks but not required for the pass gate. An explicit 'no additive look-at' fails.
- **Concrete fix:** Add an IKControl aim chain for head/arms, OR play the aim track at Action priority over Movement-priority locomotion so only conflicting limbs are overridden, OR drive the aim joints with an AnimationConstraint layered over the clip; never Stop() the walk track to aim.
- **Exemplar refs:** https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/AnimationTrack.yaml, https://github.com/Roblox/creator-docs/blob/main/content/en-us/physics/constraints/animation.md, https://devforum.roblox.com/t/inverse-kinematics-control-instance-for-animation-is-now-in-beta/1999010

### loco-fadetime-transitions

Continuity between locomotion states is governed by a live-velocity-driven blend the build OWNS, not by the stock default's fixed-time cross-fades between hard clip swaps. The discriminator is whether the build commits to continuous, live-velocity-weighted re-blending across states: passing requires the build to state that transitions between locomotion states are produced by continuously re-weighting an owned blend space as a function of live planar velocity (so adjacent states cross-blend by weight as velocity changes), rather than by the engine's fixed-duration fade between WalkSpeed-triggered clip swaps. A build that relies on the stock default fade between a WalkSpeed-keyed clip swap (no owned velocity-weighted blend) FAILS. A build that commits to a velocity-keyed blend space whose weights re-blend continuously with live velocity (e.g. a 2D blend tree keyed to planar velocity) PASSES at the architecture level; a speed-scaled stop/settle transition and a velocity-sign-flip reversal-through-intermediate push it toward full marks but the continuous-velocity-weighted re-blend commitment clears the pass gate.

- **Why above generic:** The stock Animate gives a single fixed-duration fade between discrete WalkSpeed-triggered clip swaps for free — the mean inherits exactly that. The above-generic move is continuity produced by continuously re-weighting an owned velocity-keyed blend space, so state changes are smooth weight re-blends driven by live velocity rather than timed fades between swaps. Grading that continuous-velocity-weighted re-blend commitment makes this discriminating: an owned velocity blend space expresses it, a stock fade-between-clip-swaps cannot.
- **Pass:** The build commits to continuity via continuous live-velocity re-weighting of an owned blend space (adjacent states cross-blend by weight as velocity changes); a speed-scaled stop/settle and a sign-flip reversal intermediate are credited but not required.
- **Partial:** An owned blend exists but its transition behavior is described as discrete threshold switches with a fade (not continuous velocity re-weighting), OR continuity is claimed without tying it to the live-velocity signal.
- **Fail:** Stock default fixed-time fades between a WalkSpeed-keyed clip swap; no owned velocity-weighted blend space producing continuous re-blending.
- **Evidence required:** A statement/dump showing transitions produced by continuously re-weighting an owned blend space as a function of live planar velocity (adjacent states cross-blend by weight as velocity changes) — e.g. a 2D blend tree keyed to planar velocity. A speed-scaled stop/settle transition and/or a velocity-sign-flip reversal-through-intermediate are credited toward full marks but not required for the pass gate. Reliance on the stock default fixed-time fade between a WalkSpeed-keyed clip swap does not satisfy this.
- **Concrete fix:** Drive transitions by continuously re-weighting an owned velocity-keyed blend space (adjacent states cross-blend by weight as live velocity changes) instead of relying on the stock fade between WalkSpeed clip swaps; then add a speed-scaled stop/settle and a sign-flip reversal intermediate for full marks.
- **Exemplar refs:** https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/AnimationTrack.yaml, https://devforum.roblox.com/t/hyper-realistic-animations-opensource/2087876

## Exceptional (polish)

### loco-pelvis-hip-sway-gait-phase

KILLER SYSTEM — PELVIS BIAS / HIP SWAY. The pelvis counter-rotates against the legs and sways tied to gait phase (on R15 via the LowerTorso joint), and the run is re-posed rather than a sped-up walk. The discriminator is whether the build commits to a gait-phase-driven pelvis/hip motion system: passing requires the build to state (1) pelvis/hip sway or counter-rotation DRIVEN BY gait phase (and ideally acceleration-reactive bias on starts/stops/turns), so the hips are not rigid. A build with 'no lean or pelvis sway' (rigid hips) FAILS. A build that commits to pelvis sway driven by acceleration AND gait phase PASSES at the architecture level; the figure-8 hip trace, the LowerTorso counter-rotation detail, and a re-posed run with a true airborne frame + inward/slightly-slower arms push it toward full marks but the gait-phase-driven pelvis-motion commitment clears the pass gate. Pelvis motion baked into one clip (not phase/accel-driven) or hips that move without any gait-phase coupling earns partial.

- **Why above generic:** Fourth killer system. The R15 LowerTorso/UpperTorso split exists precisely to allow hip counter-rotation, but default and AI walks leave the hips rigid — that rigidity is the floor. A pelvis sway/counter-rotation driven by gait phase (and accel-reactive) is a recognized pro tell. Grading the gait-phase-driven pelvis-motion commitment (rather than demanding a hip-position figure-8 trace + airborne-frame capture a design-stage build can't show) keeps the killer system discriminating: a build that commits to accel+gait-phase pelvis sway clears it; one with 'no pelvis sway, rigid hips' cannot.
- **Pass:** The build commits to pelvis/hip sway or counter-rotation driven by gait phase (ideally acceleration-reactive on starts/stops/turns); the figure-8 trace, LowerTorso counter-rotation detail, and a re-posed run with airborne frame + inward arms are credited but not required to pass.

### loco-velocity-lean-additive

An additive velocity/acceleration-driven lean rides on top of locomotion at runtime (not baked into a clip): the root/hips tilt toward the move direction proportional to how far movement deviates from facing — computed from dot/cross of velocity vs look vector — leaning forward on accel, into turns, back on hard stops. A lean baked into a clip (not velocity-driven) earns partial.

A velocity-driven camera bank is a cheap high-perceived-quality layer on top. Grading the runtime velocity-driven-lean commitment (rather than demanding a turn/hard-stop capture or the exact cap/Lerp values a design-stage build can't show) keeps this discriminating: a build that commits to a live-velocity lean clears it; one with 'no lean' cannot.

- **Fail:** No additive lean (explicit 'no lean'); turns and starts/stops read weightless and flat.

- **Concrete fix:** Each frame, compute velocity's deviation from facing via dot/cross, map to a capped (~10°) rotation on the root/hips, Lerp toward it (~0.2), leaning forward on accel / into turns / back on stops; optionally add camera roll from RightVector:Dot(MoveDirection).

### loco-accel-decel-momentum

The discriminator is whether the build commits to TRACKING acceleration/momentum at runtime and FEEDING it into the locomotion output: passing requires the build to state that a live acceleration (or a ramped 0..1 speedRatio over accel/decel times) is computed at runtime AND drives at least one locomotion output that reads start/stop/turn momentum (e.g. an accel-driven lean/pelvis bias, and/or the blend axis, and/or the movement-velocity multiplier). A build that tracks acceleration but feeds only one cosmetic output (lean only) without a shared blend/velocity momentum ratio earns partial-to-pass per how integrated it is, but the bare WalkSpeed snap with no acceleration tracking always FAILS.

- **Why above generic:** Default movement snaps to full WalkSpeed and stops dead with no notion of momentum — the weightless floor. The above-generic move is computing a live acceleration/momentum signal at runtime and feeding it into the locomotion so starts/stops/turns read weighted; the ceiling is one shared ramped ratio unifying blend and movement velocity. Grading the runtime-acceleration-tracked-and-fed commitment makes this discriminating: a build that already derives acceleration to drive lean/sway has the signal; the mean's instant-snap clip-swap has none.
- **Pass:** The build commits to a runtime-tracked acceleration/momentum signal (or ramped speedRatio) feeding at least one momentum-reflecting locomotion output (accel-driven lean/pelvis bias, blend axis, or velocity multiplier); a single shared ramped ratio driving both blend AND velocity is credited toward full marks.

The strongest form — one shared ramped speedRatio driving BOTH the blend axis AND the movement-velocity multiplier, with a named TweenService:GetValue easing and tuned friction — is credited toward full marks but not required for the pass gate. - **Concrete fix:** Track a live acceleration (or a dt-ramped 0..1 speedRatio over accel/decel times) and feed it into your locomotion output — at minimum an accel-driven lean/pelvis bias; for full marks drive both the blend axis and the MoveDirection velocity multiplier from one shared ramped ratio through a named easing curve and tune friction to match.

### loco-hip-height-terrain

Vertical grounding adapts to terrain at runtime so the character is not flat-clipping/floating over slopes and steps — via a runtime pass that adjusts foot (and ideally root/hip) vertical placement to the actual ground. The discriminator is whether the build commits to a runtime terrain-vertical-grounding pass at all: passing requires the build to state a runtime grounding pass (foot IK via IKControl/Motor6D.Transform, or equivalent) that places feet on the ACTUAL ground height of slopes and steps rather than the flat clip plane, so the character conforms vertically to terrain. A build with NO runtime grounding pass — feet on the flat clip plane that skate/float on slopes — FAILS. A build that commits to a runtime foot-grounding pass that plants feet on slopes and steps PASSES at the architecture level; the CEILING form (credited toward full marks) is additionally offsetting the root/hip vertical position from the height delta between the two foot-IK targets, clamped, so both feet plant with naturally bent knees on inclines and corner-steps. A foot-grounding pass that plants feet on slopes/steps but says nothing about root/hip height earns a solid pass (it conforms to terrain); only a build with no grounding pass at all FAILS.

- **Why above generic:** Default clips play on a flat plane and float/clip over slopes and steps — no vertical terrain awareness, the floor the engine hands you. The above-generic move is a runtime grounding pass that conforms feet to the real ground height; the ceiling is also dropping/raising the root from the inter-foot delta for natural knee bend. Grading the runtime terrain-grounding commitment makes this discriminating: a foot-IK-equipped build conforms vertically to terrain, a no-IK flat-clip build cannot.
- **Pass:** The build commits to a runtime foot-grounding pass (IKControl/Motor6D.Transform) that places feet on the actual slope/step ground height; a coupled clamped root/hip offset from the inter-foot delta is credited toward full marks but not required to pass.

- **Fail:** No runtime grounding pass at all; feet ride the flat clip plane and float/skate over slopes and steps.

The CEILING — a root/hip vertical offset computed from the height delta between the two foot-IK targets, clamped, so both feet plant with bent knees on inclines/corner-steps — plus a stairs/slope capture are credited toward full marks but not required for the pass gate. A build with no runtime grounding pass (flat-clip feet that skate/float on slopes) does not satisfy this.
- **Concrete fix:** Add a runtime foot-grounding pass that raycasts to the actual ground and places each foot on the true slope/step height; for full marks also offset the root/hip toward the lower foot from the inter-foot-target height delta (clamped) so both feet plant with natural knee bend on inclines and corner-steps.
