Assuming you are referring to memtrace—the recently popular local, MCP-native
structural memory layer for AI coding agents—whether there is a better project
depends entirely on what you are optimizing for.

While memtrace is excellent for zero-config, cross-editor local memory, it can
struggle if you need deep temporal reasoning, enterprise scalability, or
integration outside of local coding environments. Here are the top alternatives
that complete the same job, categorized by where they excel.

1. mem0 (Best for Production & Ecosystem Scale)
Formerly known as Embedchain, mem0 is currently the industry standard for
universal agent memory.
 * How it works: It uses LLM-based extraction to identify facts from
   interactions and embeds them in a vector database for semantic retrieval
   (with optional knowledge graph support).
 * Why it's better: If you are building AI applications or need memory that
   scales beyond a single developer's machine, mem0 offers unparalleled
   cross-platform support and API integrations.
 * The trade-off: It is optimized for cloud/API workflows and general-purpose
   agents, lacking the instant, out-of-the-box local AST (Abstract Syntax Tree)
   indexing that makes memtrace so fast for coding.

2. zep (Best for Temporal & Complex Reasoning)
If your agent frequently gets confused by outdated context (e.g., remembering
how auth used to work instead of how it works now), zep is the superior
architectural choice.
 * How it works: Built on its graphiti engine, it stores facts as nodes in a
   knowledge graph with explicit temporal metadata. It tracks exactly when a
   fact became true and when it was superseded.
 * Why it's better: It natively understands the evolution of a codebase. Its
   graph-first structure handles multi-hop logical queries much better than
   standard vector search.
 * The trade-off: Self-hosting is heavy. You have to manage a graph database
   and the full engine, unlike the lightweight SQLite/local footprint of
   memtrace.

3. Alternative Local MCP Servers
If you love the local, Model Context Protocol (MCP) workflow of memtrace but
want different underlying mechanics, the open-source community has a few direct
competitors:
 * memorygraph: A direct alternative that uses a local graph database to map
   relationships between files and concepts, focusing heavily on semantic
   connections rather than just structural ones.
 * memora: An MCP memory server featuring "Hebbian learning"—meaning the
   connections between coding concepts strengthen the more the AI agent
   traverses them, and weaken through disuse.
 * lorekeeper: A self-improving MCP server that combines hybrid search with an
   auto-linking knowledge graph and a UI dashboard for manual memory management.

4. Native Editor Memory
 * Why it's better: If you only use one IDE (like cursor or windsurf), relying
   on their built-in project knowledge tools is completely frictionless. You
   don't need to manage separate MCP servers or background processes.
 * The trade-off: You lose cross-agent portability. A memory saved in cursor
   cannot be accessed by claude code in your terminal, which is the exact
   problem memtrace was built to solve.

Feature Comparison

|----------------|-----------------------------------|-------------------------|--------------------|
| memtrace       | local, cross-agent coding memory  | bi-temporal graph / ast | local, mcp-native  |
| mem0           | universal agent memory at scale   | vector (graph optional) | cloud / self-hosted|
| zep            | temporal reasoning & relationships| knowledge graph         | cloud / self-hosted|
| memorygraph    | local graph-based mcp alternative | graph database          | local mcp server   |
| cursor/windsurf| zero-friction single-editor       | proprietary vector/text | baked into editor  |

Short version: the list you got was solid, but it left out the three tools that
matter most for an "all-rounder" verdict — Letta (formerly MemGPT), Cognee, and
Supermemory — and independent testing is blunt that there's no single winner.
The best pick forks on one question: do you want general agent memory, or
specifically memtrace's lane (local, MCP-native, coding agents)?

For a general-purpose all-rounder, Mem0 is the consensus pick: biggest
community, easiest drop-in API, hybrid vector + graph + key-value storage, runs
managed or self-hosted. Its one real weakness is temporal reasoning — it
overwrites facts without versioning, so on the LongMemEval benchmark it lands
around 49% versus Zep/Graphiti's ~64%. So if "all-round" for you leans toward
accuracy and handling facts that change over time (how auth *used* to work vs
how it works now), Zep is the stronger engine — just heavier to self-host.
Worth noting those benchmark numbers originate from Zep's own research and Mem0
disputes the methodology, so treat the gap as directional, not gospel.

If what you actually want is memtrace's exact niche but more well-rounded, two
beat it there:

- Supermemory — MCP-native, purpose-built for Claude Code / OpenCode, and adds
  semantic recall plus explicit "forgetting" that memtrace's pure structural/AST
  approach doesn't do. Caveat: its benchmark claims are self-reported and
  unverified.
- Cognee — fully local (runs on Ollama, zero cloud), poly-store graph + vector +
  relational, ~6 lines to get going. It's the best bridge if you want memtrace's
  local/private footprint but general-purpose memory instead of code-structure
  only.

My honest one-liner: Mem0 if you want the safe generalist, Cognee if keeping
everything local and private matters as much as it clearly did when you picked
memtrace. Zep only if temporal accuracy is the thing you're actually chasing.

The reason the "best" genuinely shifts is that memtrace does something narrow
and deterministic (AST/code structure, no LLM calls), while these others do
fuzzy conversational/entity memory — "all-rounder" only has a clean answer once
you know which of those you can't live without.

That setup makes the call much clearer, and it's not the one from before. Your
binding constraint isn't storage type or temporal reasoning — it's that two
orchestration agents (Claude Code and Gemini CLI) plus a growing pile of MCP
tools all need to share one memory, or each agent keeps re-learning your project
from scratch. That's the cross-agent problem, and memtrace is actually a weak
fit for it: it only ever remembers the *code* slice. It won't hold your Gemini
image-gen settings, Trellis params, Blender export conventions, or Roblox naming
rules — which is most of what a pipeline like yours needs to carry between
sessions and between agents.

Best fit for you: OpenMemory MCP, from the Mem0 team. It's a single *local*
memory store exposed over MCP, built specifically to sync across MCP clients —
Claude and Cursor are the headline integrations, and Gemini CLI is a first-class
MCP client too, so both your agents can read and write the same store. Local by
default (matches your Blender/Trellis-on-your-machine workflow), general-purpose
rather than code-only, and about as close to "the all-rounder for a growing MCP
stack" as exists right now.

If you want more structure as the tool web keeps growing, Cognee is the heavier
local alternative — an actual knowledge graph (graph + vector + relational, runs
on Ollama) that can map relationships across your assets, tools, and decisions.
More setup, but it pays off if the graph itself becomes something you query.

The reframe I'd push, given "the tools are just growing": these aren't
either/or. memtrace is genuinely good at code structure; OpenMemory is good at
shared cross-agent project knowledge. Running memtrace for the code plus a
shared memory layer for everything else is a legitimate stack — a sprawling
toolchain usually wants the *right memory per job*, not one tool pretending to
do all of it. The one real weakness of the Mem0 family is temporal accuracy (it
overwrites facts instead of versioning them); if you catch it clinging to stale
conventions, Zep/Graphiti is the temporal upgrade — just not as plug-and-play
over MCP.

Yes to Obsidian — but slot it in as one specific layer, not another general
memory tool. It's local markdown with a graph view, and the MCP support is
mature now: there are several vault MCP servers, plus an "Agent Client" plugin
that runs Claude Code, Codex, and Gemini CLI *inside* the vault. What makes it
worth adding is the thing the others can't do — it's the *human-readable,
human-editable* source of truth. OpenMemory is the memory your agents talk to
and you mostly don't look at; Obsidian is the design bible, decision log, and
asset catalog that you curate and the agents read from. Keep that split clean:
don't make Obsidian the agents' high-frequency scratch memory (markdown's bad at
that), make it the durable knowledge the whole stack points back to. The payoff
is one source, two audiences — agents append notes, you refine them, and the
vault is simultaneously your documentation and their context.

On tracing the game's progression, your "give it its own memtrace" instinct is
half right, and worth pulling apart. memtrace already *is* a bi-temporal,
per-project trace, so scoping one memtrace index per game hands you the code
timeline for free — what changed, what'll break, recency. That part's correct:
one memtrace per game.

But a game's progression runs on three timelines, and code is only one of them:

- Code -> memtrace per project (your idea).
- Design/decisions -> a dated decision log in Obsidian: "2026-07-16: swapped the
  jump mechanic from X to Y because Z." This is the *why the game became what it
  is* trace — the one you'll want most in six months, and the one no memory tool
  records for you. It has to be written, ideally by the agent as a pipeline step.
- Asset lineage -> the one people forget, and the most valuable for a
  *generative* pipeline like yours. Every Roblox asset has a provenance chain:
  Gemini prompt -> image -> Trellis run (seed/settings) -> Blender ops -> Roblox
  object. Record that as a small "asset card" (JSON, or frontmatter on an
  Obsidian note) and you can trace how any asset was made and regenerate it
  deterministically. Provenance tracking for AI-generated 3D is a named practice
  now. Version the binaries themselves with git-LFS or DVC.

So don't give the game *a* memtrace — give it a trace *stack*: memtrace for
code, an Obsidian decision log for design, provenance cards for assets, all
sitting on git as the actual timeline. Your instinct ("its own thing, scoped to
this game") is right; it's just that the "thing" is a per-game namespace across a
few complementary tools, not a single one.

And since your whole stack is already local + MCP + git, the real move is to
make the trace maintain itself: have Claude Code / Gemini append to the decision
log and write asset cards *as pipeline steps*, so progression gets recorded as it
happens instead of whenever you remember to journal it.
